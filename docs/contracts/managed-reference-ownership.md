# Managed DSL reference ownership

Dockerfile, GraphQL, Handlebars, Proto, Mustache and Jinja reference producers
retain dependency/type/fragment/lookup/section-test/helper-invocation facts in a
closed, versioned internal `managedReferenceFacts` envelope. It binds the admitted
source text, UTF-16 coordinates, exact reference values, optional source owners
and explicit partial coverage. These observations do not certify execution or
complete runtime dispatch. Unknown positions and owners remain null.

The previous six custom adapters formed Cartesian products between file exports
and file-wide references. No occurrence or syntax kind participated in those
pairs. The original Mustache counterexample therefore attached `bravo` to `first`
and `alpha` to `second`. Those pairs are obsolete representations of reference
adjacency, and are replaced with the original positive reference content and its
source owner. Imports, exports and usages retain their existing roles.

GraphQL retains NamedType versus FragmentSpread kinds and declaration intervals;
display titles such as `type Amber` remain separate from semantic owner `Amber`.
Dockerfile dependencies retain instruction ranges and their stage owner.
Handlebars explicit static helper syntax remains distinct from value lookup and
partial dependency references. Inline definitions provide source owners. Jinja
macro/block scopes retain their complete lexical ranges and explicit invocation
syntax; declaration names are not invocation evidence. Django does not acquire
Jinja call semantics. Mustache lookups and section tests remain reference facts,
including lookups whose names contain spaces. Proto reflection type references
remain file-scoped without fabricated source coordinates.

File relation normalization retains the internal envelope for incremental bundle
replay. Chunk projection emits `referenceDetails` with their original semantic
owner, plus explicit `referenceCoverage`; source intervals select observations
without a display-name join. Parsed envelopes are strictly admitted and frozen.
Validation is memoized only for these immutable objects, and source-range lookup
uses one retained index plus binary search per chunk. Unqualified or malformed
envelopes report unavailable reference coverage.

The canonical `file_relations` schema also validates this optional envelope
strictly. Semantic validation checks exact counts, source extents and owner IDs;
unknown fields and kinds cannot pass through generic relation extension fields.
Artifact validation leaves the caller's mutable input mutable, while runtime
admission freezes retained evidence. Ordinary and sharded publication controls
retain complete content plus invalid-count/owner/range/extra-field negatives.

Ordinary calls and canonical call-site output cannot be filled with these
reference facts. This rule applies independently of lexicon preferences, missing
lexicons and direct chunk consumers. A partial capability label alone is not
admission authority. Other languages' existing qualified invocation producers
remain unchanged; native managed-language call controls are preserved.

The six pair loops and the test helper's requirement for a call to every expected
usage are replaced together. Positive import/export/usage assertions remain;
typed facts and actual chunk/replay handoffs are added. Handlebars allocation
controls retain their exact original frame/range assertions and now require the
lookup kind. No fixture is removed or skipped. Shared graphRelations advances
2→3, sourceChunking 31→32 and callFlow 49→50 to retire derived old meanings.

`managed-reference-kind-and-owner.test.js` follows actual parsers, registered
adapters, lexical admission, call indexing, production chunking, canonical
call-site writing and incremental bundle replay. Cross-owner negatives, explicit
helper positives, reflection limits, malformed kind/envelope rejection and the
ordinary JavaScript call control remain distinct. Functional execution is deferred
and belongs to the implementation receipt, not this authored contract.

Handlebars inline declaration directives are excluded from helper invocation
observations in the shared parser and source-linked registry consumer. The
specific template registry adapter advances 2→3; a same-named registry helper
cannot turn an inline declaration into a navigation target. Its existing real
helper/partial, block-local shadowing, cycle, authority and canonical sink/detail
controls remain intact, with the declaration negative added.
