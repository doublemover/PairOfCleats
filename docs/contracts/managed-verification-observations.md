# Managed verification observations

The original managed verifier captures its result or thrown value before reading
settlement. The existing storage-observation ledger retains that first observer,
the original nested receipt, field inspections and callback failures. Every
settlement/capability field checks all retained prerequisites before and after
access. A later field cannot erase an unconfirmed interval in an enclosing owner.

Receipt shape remains exact: `resourceId`, `settled:true`, `pending:false`, with
the actual invocation identity and no unknown enumerable fields. A positive
verification remains an object. Successful capture and arbitrary copied receipt
fields do not provide independent native-close proof. The existing install/reuse
owners retain their resource phase until actual original work and exact recovery
requirements are satisfied.

The selected-generation consumer reads the same private result observation,
including nested receipt prerequisites. Diagnostic aggregation uses an own data
message; it does not invoke a pending original message accessor. Frozen and
function-valued failures retain their original cause/receiver. Ordinary receipt
getter failures retain their existing explicit recovery path.

Nine authored, locally unrun controls exercise the actual verifier with finite
result/receipt/inspection models: early result/failure observations, nested and
enclosing guards, capability revocation, independent inspection/callback errors,
function failures, exact refusal and the original closed positive. These models
do not qualify vendor packages, native handles or real child retirement.

Broader publication/diagnostic phase integration and native execution remain in
the installer acceptance scope.
