# Explicit Python and Ruby LSP profiles

Implementation status: UNVALIDATED. These selectable source paths have not been run against upstream binaries. They are experimental and do not qualify the versions listed in issues #1157/#1158.

The existing `tooling.lsp.servers[].preset` surface accepts distinct `basedpyright`, `ty`, `pyrefly` and `ruby-lsp` profiles. They are excluded from automatic preset collection. Selecting one Python alternative suppresses the dedicated Pyright contribution for that selection; selecting multiple alternatives fails explicitly. An explicit provider-ID pin to Pyright remains available. Missing/unavailable alternative output does not silently switch engines. Ruby LSP similarly replaces a simultaneous Solargraph contribution while preserving Solargraph's separately named existing route.

Launch argument arrays follow upstream [BasedPyright](https://docs.basedpyright.com/latest/configuration/language-server-settings/), [ty](https://docs.astral.sh/ty/editors/) and [Pyrefly](https://pyrefly.org/en/docs/IDE/) integrations. Actual capabilities are negotiated by the shared LSP owner. The profiles require observed profile receipts for durable provider cache reuse; adapter metadata is not binary/version admission. Interpreter/venv, version/platform, roots/stubs/checking policy and config precedence still require host profile mapping and comparative fixtures before any default promotion. Ruff remains a complementary diagnostic/format profile; Jedi remains deferred navigation-only pending a separate qualified implementation.

[Ruby LSP](https://github.com/Shopify/ruby-lsp) can compose a bundle and activate project add-ons. Its profile requires an exact launching-repository trust grant before preflight or runtime launch. The Ruby-specific signature parser retains `def` signatures as presentation only and does not infer Solargraph/YARD type equivalence. Bundler/Gemfile.lock/add-on/version selection and no-download launch qualification remain pending.

The authored fixture `tooling/providers/explicit-python-ruby-profiles` covers explicit launch mapping, auto-selection exclusion, baseline pin preservation, duplicate-engine rejection and Ruby presentation boundaries. Installation/detection/doctor recipes, upstream version/bytes admission, actual environment/config semantics, retained artifact/query acceptance and cancellation/crash measurements remain required; these partial source changes close neither issue.
