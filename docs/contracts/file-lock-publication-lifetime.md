# Generic file lock publication lifetime

Status: source implementation and authored regressions are **UNVALIDATED**. Native filesystem and cross-process qualification remain deferred.

`acquireFileLock` serializes and checks the generated PID, lock ID, and start time before opening a file. After exclusive open succeeds, every write, identity, and close failure belongs to that publication attempt. An `ENOENT`, `EEXIST`, or Windows `EPERM` thrown after open cannot enter parent creation, stale cleanup, or another acquisition attempt.

The publication captures the original descriptor's `stat`, `writeFile`, and `close` methods with their receiver. Successful close is recorded only after its promise fulfills. A failed native close receives no automatic retry. Publication failure preserves its original cause, including frozen objects and `undefined`, `null`, `false`, zero, or an empty string; independent original pending observations and failures inspecting those observations remain represented.

The failure exposes a non-enumerable `fileLockPublicationSession`. `isFileLockPublicationSession` recognizes only actual producer capabilities in this process. `releaseAfterClose()` coalesces concurrent reconciliation, explicitly retries the captured original close, checks every captured independent observer, and removes only the original sealed physical metadata. Its receipt is `{ resourceId, settled: true, pending: false }`. It never replays a failed write or replaces a failed identity observation with path-only ownership. A true pending marker without an observer, an unreadable observer, or a throwing observer cannot authorize removal. The original error's `cacheOwnershipReleased()` follows eventual exact reconciliation.

Physical identity uses the original descriptor's device, inode, birth time, single-link regular-file status, byte extent, mode, and modification/change timestamps. Failed publication seals the latest successful descriptor observation; changed or unsealed metadata remains intact. Some filesystems commit timestamps only at native close, which can conservatively block rollback after a close failure. No timestamp mismatch is silently adopted. If the original pathname is already absent, confirmed descriptor closure and independent settlement can complete without deleting anything. Renamed metadata is neither discovered nor removed.

Successful publication seals its metadata snapshot after confirmed descriptor close. Normal `lock.release()` checks that snapshot and the captured original lock ID; a copied ID, replaced inode, or modified record does not acquire deletion authority. Repeated normal release still reports false after removal. This strengthens the original owner release without changing ordinary successfully published lock payloads or PID/age stale handling.

While an actual descriptor publication or failed publication capability remains unsettled, the existing acquisition, stale removal, asynchronous owner removal, and synchronous owner removal paths refuse deletion of that lexical pathname in this process, including force and exact logical-ID requests. This is an in-memory guard in the existing owner, with no new filesystem namespace. It does **not** coordinate another process, survive this process, discover physical aliases, or confer protection on raw filesystem operations. Existing ordinary stale-lock recovery in other processes is unchanged. Portable Node filesystem APIs also do not provide atomic compare-and-unlink; external replacement between the final identity check and unlink remains a platform qualification limit. These changes do not claim a cross-process durable publication protocol or native filesystem acceptance.

Fixture disposal does not stand in for settlement of deliberately unknown owners. The existing ordinary lock and falsey worker/release fixtures remain applicable. No fixture, syntax, lint, format, bootstrap, or native execution was run for this batch.
