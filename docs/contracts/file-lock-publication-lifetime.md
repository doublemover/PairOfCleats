# Generic file lock publication lifetime

Status: source implementation and authored regressions are **UNVALIDATED**. Native filesystem and cross-process qualification remain deferred.

`acquireFileLock` serializes and checks the generated PID, lock ID, and start time before opening a file. After exclusive open succeeds, every write, identity, and close failure belongs to that publication attempt. An `ENOENT`, `EEXIST`, or Windows `EPERM` thrown after open cannot enter parent creation, stale cleanup, or another acquisition attempt.

The publication captures the original descriptor's `stat`, `writeFile`, and `close` methods with their receiver. Original independent write/stat/close observations must permit native destruction before the captured close is invoked. A rejected promise alone cannot establish native settlement, even if another primary observer already returns true. Successful close requires the native method's standard `undefined` fulfillment; every nonvoid result remains unconfirmed. A failed native close receives no automatic retry. Publication failure preserves its original cause, including frozen objects and `undefined`, `null`, `false`, zero, or an empty string; independent original pending observations and failures inspecting those observations remain represented.

Original resource observations precede diagnostic inspection. The first primary's message is read once and its own property descriptors are captured once, before close; later error projections preserve original getter/setter receivers and read-only attributes without adopting replacements. Failures enumerating or projecting descriptors, reading the message, or invoking an original resource observer remain in the bounded inspection history with their own independent original observers. A primary that later confirms settlement cannot erase an independently pending inspection failure. Unreadable ownership stays unknown; history overflow stays pending.

The failure exposes a non-enumerable `fileLockPublicationSession`. `isFileLockPublicationSession` recognizes only actual producer capabilities in this process. `releaseAfterClose()` coalesces concurrent reconciliation, checks every captured independent observer before explicitly retrying the captured original close, and removes only the original sealed physical metadata. Its receipt is `{ resourceId, settled: true, pending: false }`. It never replays a failed write or replaces a failed identity observation with path-only ownership. A true pending marker without an observer, an unreadable observer, or a throwing observer cannot authorize close or removal. Only the exact same-owner outward failure, authenticated by private producer identity, is excluded from recaptured original observations: its own settlement depends on the close it cannot itself gate. An error merely carrying that actual session remains independent. The original error's `cacheOwnershipReleased()` follows eventual exact reconciliation.

Rollback captures a failing pathname lookup's original observation before reading its error code. Pending work cannot become `ENOENT` absence evidence, and diagnostic getter failures cannot replace that original failure. The owner checks original settlement again after the awaited identity lookup and after removal. Removal requires standard void fulfillment in both failed-publication rollback and the ordinary successful owner's release. If actual removal succeeds while an original independent observer becomes pending, the publication fence and failed receipt remain; later explicit settlement can finish without another native close, write, or unlink. These checks do not make the final compare-and-unlink atomic.

Physical identity uses the original descriptor's device, inode, birth time, single-link regular-file status, byte extent, mode, and modification/change timestamps. Failed publication seals the latest successful descriptor observation; changed or unsealed metadata remains intact. Some filesystems commit timestamps only at native close, which can conservatively block rollback after a close failure. No timestamp mismatch is silently adopted. If the original pathname is already absent, confirmed descriptor closure and independent settlement can complete without deleting anything. Renamed metadata is neither discovered nor removed.

Successful publication seals its metadata snapshot after confirmed descriptor close. Normal `lock.release()` checks that snapshot and the captured original lock ID; a copied ID, replaced inode, or modified record does not acquire deletion authority. Repeated normal release still reports false after removal. This strengthens the original owner release without changing ordinary successfully published lock payloads or PID/age stale handling.

The successful handle retains its same non-enumerable actual `fileLockPublicationSession`. A direct release rejection retains its exact value, including frozen/falsey values; the owner separately captures original observations before diagnostic inspection and restores its existing process-local fence. Every explicit subsequent release checks those original observations before another lookup, owner read, or removal, after the awaited metadata inspections, after removal, and before acknowledgement. A fulfilled/rejected native promise and a replacement public observer do not authorize another native attempt. `releaseFileLockOrThrow` receives the producer's privately associated prerequisite observation in addition to the raw rejection, so even a message getter that replaces the raw observer before wrapper diagnostics cannot clear the original owner.

Direct release and the actual session share one metadata operation. Exact session reconciliation can complete without consuming the handle's one successful release acknowledgement; the later handle call acknowledges confirmed removal without another unlink, and subsequent calls return false. If actual removal finishes while original native work becomes pending, the fence remains and the next reconciliation waits for that original work; it does not repeat unlink. The existing exact identity and absence rules still apply. Session receipts require original settlement plus confirmed removal. Failed published-release error observations describe only independent native prerequisites, so their own metadata predicate cannot block the retry needed to settle it.

Only the actual wrapper producer can associate its outward error and captured independent observer with the exact published handle. The new independent worker/inspection/native prerequisites return to the same existing owner before another explicit retry, using both private producer identities. If that error is thrown back into the same owner or wrapped again, the owner retains its independent observations without feeding its own predicate back into itself. A copied error, session field, serialized handle, or error merely carrying an actual session has no such identity. Unbranded cyclic observers stay unconfirmed through a bounded reentrancy check; they never become removal authority. The publication and release modules depend one-way on the dependency-free `file-lock-producer-observations.js` leaf holding their existing private handle/failure associations. The native owner and its existing path fence stay in publication; there is no producer-module cycle or eager config, repository-path or storage-layout load.

While an actual descriptor publication or failed publication capability remains unsettled, the existing acquisition, stale removal, asynchronous owner removal, and synchronous owner removal paths refuse deletion of that lexical pathname in this process, including force and exact logical-ID requests. This is an in-memory guard in the existing owner, with no new filesystem namespace. It does **not** coordinate another process, survive this process, discover physical aliases, or confer protection on raw filesystem operations. Existing ordinary stale-lock recovery in other processes is unchanged. Portable Node filesystem APIs also do not provide atomic compare-and-unlink; external replacement between the final identity check and unlink remains a platform qualification limit. These changes do not claim a cross-process durable publication protocol or native filesystem acceptance.

Fixture disposal does not stand in for settlement of deliberately unknown owners. The existing ordinary lock and falsey worker/release fixtures remain applicable. No fixture, syntax, lint, format, bootstrap, or native execution was run for this batch.

The successful owner's metadata read now borrows an actual FileHandle through the existing contained descriptor owner, using its sealed original byte extent and physical stat. It is lazy-loaded at this consumer, so path-only lock imports do not eagerly load the descriptor/scheduler graph. Read/stat/close failures propagate to the same publication owner; native close failure withholds unlink and exposes only actual privately validated contained-file capabilities. A child close-only recovery never rereads metadata or removes a lock. Explicit parent reconciliation revalidates the current metadata after child settlement. See [the metadata reader contract](file-lock-release-reader-lifetime.md).

Original worker prerequisites now join this same owner before the first cleanup invocation, retaining the existing fence and exact reconciliation order; see [worker lifetime](with-file-lock-worker-lifetime.md). Authenticated same-owner metadata failures remain distinct from independent worker resources and cannot create a self-cycle.

Other diagnostic/stale `readLockInfo` callers still use opaque `fs.readFile` and catch-to-null fallback; their lower descriptor ownership and swallowed read failures remain open. Other raw readers and atomic publication owners also remain separate. No metadata witness is granted to arbitrary wrapper causes, and no issue completion or native acceptance is asserted.
