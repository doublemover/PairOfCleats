# Revision oracles

The registered `tiny-javascript-source-revisions-v1` adapter now feeds exact
generated source bytes through the real JavaScript AST and chunk owners. Its
closed grammar admits up to eight files with eight distinct, constant-return
function declarations each, sixteen edits and Babel/Acorn/Esprima selection.
Mutation records contain data, never supplied source templates or commands.
Edits bind exact before/after states; deleted paths retract, changed files reparse
and unchanged files reuse immutable projections within the original invocation.
Every checkpoint also runs an uncached parser/chunker build.

An independent construction-grammar interpreter imports no parser, chunking,
range, source-snapshot or cache helper. It derives exact function/export ranges,
names, kinds, UTF-16 positions, line numbers, declaration text and UTF-8 hashes.
Empty modules, BOM, CRLF and an astral comment containing a decoy declaration
are explicit grammar productions. This is a source-extraction claim within that
grammar; it establishes no function execution, full index, semantic closure or
publication claim. A fresh candidate agreeing is a separate differential claim.

Strict scenario/output/receipt schemas live in `revision-source.js`. Receipts
retain actual source-unit/path/namespace identities, original byte/text hashes,
line starts, observed parser family/version/options, declaration identities and
current shared producer versions. No cross-repository identity is normalized.
Private original execution handles own runs and retirement; diagnostic comparisons
cannot adopt receipts. The common revision-deletion minimizer requires the same
independently failing checkpoint, and reruns the registered producer/reference.

Runs allow at most 1,000 ms, 64 KiB of source per state and 256 KiB of receipts.
Reference-file bounds can be tightened to zero; exhaustion is unknown while
fresh-build parity remains separately visible. Cancellation preserves its original
reason and publishes no successful handle. All checkpoints remain represented
after an admission stop. Eight fixture cases are authored and locally unrun;
they include corrected controls and seeded stale/range/content/identity defects.
Build-world, full-index, certificate-consumer and suggestion adapters remain open.

The closed offline adapter `finite-positive-support-revisions-v1` supplies the
first bounded cross-revision profile for #1528. It drives the existing positive-rule
view owner and compares each result with a fresh build and an independent finite
reference. It accepts data records, never generated commands or candidate code.

Scenario and execution contracts live in
`src/contracts/schemas/revision-oracle.js`. Scenarios retain the supplied world,
fixed definition, generator family/seed, exact support-origin identities and
ordered edits. Every edit binds the original before-state hash and independently
realized after-state hash. All edits are checked before candidate work; stale
hashes, absent removals, reused origins and unsupported profiles are refused.
Input capture rejects accessors and unknown fields. This profile allows no source
references and makes no current source-authority claim.

The model is limited to sixteen facts, twelve intensional Boolean facts, thirty-two
positive conjunctive rules, sixty-four extensional supports and sixteen edits.
Duplicate supports for one fact retain separate origins. Membership is Boolean;
provenance is the bag of direct producers, including duplicate rule bodies and
support multiplicity. It is not the bag of all derivation paths through a recursive
program. Anti-join, negative dependencies, compiler/source revisions, mutable heap,
storage/reload and test-selection adapters remain outside this first profile.

The reference enumerates all intensional valuations with the exact supplied
extensional membership, then intersects every Horn-closed valuation. It does not
import candidate extraction, fixedpoint, propagation or support hashing. Direct
producer terms are reconstructed from the resulting model and compared with
multiplicity and original origin identities. Independently checking that declared
finite model does not establish the correctness of a source-to-model frontend.

Each checkpoint records separate candidate/rebuild execution IDs, root and output
identities, independent and differential claims, work counters and separate phase
timings. Fresh-build equality cannot establish independent correctness. Incomplete
candidate output or exhausted reference enumeration yields unknown. A run preserves
every declared checkpoint, including not-run rows after a work/output stop. Default
execution allows 1,000 ms, 4,096 valuations per reference and 256 KiB of receipts;
callers may only tighten work bounds. No runtime/performance result is claimed from
these limits. Cancellation propagates without a successful execution handle.

Private original handles own completed runs. Inspection cannot adopt copied
receipts; retirement drops the retained scenario/run. The diagnostic data comparison
API deliberately creates no qualified execution receipt.

Revision-deletion minimization requires an actual independent disagreement from
the original run. It keeps the original scenario and named checkpoint/fact
predicate. Every proposed deletion rechecks transition preconditions and re-executes
the registered owner/reference. Unknown, unsupported or invalid proposals cannot
replace the reproducer. Attempts are bounded to sixty-four and 1,000 ms; this is
revision deletion, not a claim of globally minimal source or program behavior.

Seven authored, locally unrun fixture cases cover deterministic families and seeds,
simultaneous inputs, duplicate supports, recursive seed removal/re-addition, stale
preconditions, original handles, cancellation, explicit unknown outcomes and
minimization. Seeded diagnostic defects must be detected while corrected outputs
pass. The minimizer's injected finite boundary control tests its decision logic;
it does not claim the real positive-rule owner currently fails.

The `finite-relational-revisions-v3` adapter drives the original
[join/anti-join cohort](relational-join.md), [select/project](selected-adjacency.md)
and [grouped views](grouped-adjacency.md). It supports eight original supports
per input, eight copies per support and sixteen exact-hash edits. Its reference
recounts the complete contribution history, expands tiny occurrence bags and
compares exact endpoint/parent multiplicities, captured-domain observations and
the actual emitted relation cardinality. Group minima/maxima use complete tiny
copy expansion and preserve all parent alternatives. Incomplete groups emit no
exact aggregate facts; known positive select/project copies remain available.
It imports no candidate arrangement, coefficient or delta helper. Fresh relation
content is compared separately; private transition ledgers legitimately give
different view roots. It does not normalize the actual relation content away.

Scenario/receipt contracts are version 3 in `revision-relational.js`. Earlier
profiles/scenarios/receipts and the `maxReferencePairs` option are rejected; regenerate
them under the current contract. All original binary families/assertions remain.
Reference pair/copy examinations use `maxReferenceWork`/`referenceOperations`,
bounded to 4,096 per checkpoint and cooperative execution to 1,000 ms. Exhaustion
is unknown even when rebuild parity passes. Receipts retain all checkpoints and
at most the first full independent counterexample, with exact output hashes and
failure outcomes for subsequent disagreements, under 256 KiB. Diagnostic data
comparison does not create an original execution handle. Nine authored,
unrun cases cover actual registered operators, seeded cross-term/threshold and
origin/multiplicity defects, unary retraction, false aggregate cardinality and
partial-domain exactness, stale worlds, unknown and handle retirement. This
profile has no source materializer or durable publication. Both finite profiles
share the bounded revision-deletion engine. Relational minimization requires the
same named checkpoint's independent bag disagreement; positive-rule minimization
additionally preserves the named fact. Every proposal runs its original registered
candidate/reference and retires its temporary execution handle. Unknown, invalid,
corrected or different failures cannot replace the witness. One additional authored,
unrun finite boundary control exercises these decisions without forging a production
execution or claiming either current candidate fails.

Version 3 retains each operator's actual maintenance strategy and work counters.
Join receipts include pair terms/support hashes; grouped receipts include affected
groups/group hashes; selected receipts include support hashes. Their closed schemas
are tied to the declared operator. No full-recomputation label is fabricated for
incremental work, and a copied metric from another operator is rejected. Bounded
generators exercise each real sparse owner through the existing independent and
clean-rebuild comparisons. Operator work stays separate from measured elapsed
time and reference examinations; original bounds are unchanged.

## Published code-index revision cohorts

The explicit `published-javascript-chunk-index-revisions-v1` adapter materializes
the same inert construction grammar in a fresh task-owned workspace. It invokes
the real `build_index.js` stage2 code-publication owner in serial fresh children:
one persistent incremental candidate and a new repository/cache for each clean
rebuild. Each checkpoint starts from its exact declared source state. Selecting
nonadjacent checkpoints models a batch edit; omitted checkpoints are enumerated,
and `completeScenarioCoverage` stays false. No author cache or fixture-health
stamp can substitute for a build.

The fixed configuration selects Babel without Flow and disables embeddings,
SQLite and semantic enrichment for this chunk-index profile. It keeps the
production worker backend and uses one indexing thread. Generated files are
data: no source template, command, project hook or caller executor is admitted.
Only these constructed repositories receive explicit child-launch trust.
Application roots/test hooks are isolated in the child environment; the parent
environment is unchanged. Normal bootstrap readiness still gates the real build.

The original strict artifact loader streams bounded rows from the selected
published generation under actual storage reader leases. Source bytes are
checked before/after, and the same bounded current-pointer hash must survive the
read. The independent grammar compares names, kinds, UTF-16 intervals, lines and
exact source text. Truly zero-byte files are absent from the indexing universe;
that explicit eligibility rule is separate from source extraction's root module.
Clean-rebuild parity also compares **exact chunk UIDs and published tokens**.
`token-flow.js` selects the `repo` namespace, and `identity/chunk-uid.js` binds
relative virtual paths and source/context bytes: independent repository/cache
roots do not justify dropping these identities. No provenance is normalized.
Missing token payloads remain explicit null, without a token-completeness claim.

Strict `revision-index.js` receipts retain actual commands, configuration hashes,
exit status, Node/ABI and producer versions, generation/pointer identities,
per-stream log hashes/counts, checkpoint coverage, distinct oracle claims and
counterexamples. Complete stdout/stderr is retained under the disposable marked
workspace; truncated or lossy capture refuses qualification. Success does not
establish semantic closure, SQLite/vector correctness, source execution, native
backend activation or a general latency improvement.

Private original handles own physical worlds and readers. Joined `recheck`
callers receive the exact tracked promise, with a three-second operation cap and
at most16 admitted rechecks. Rechecks require the original pointer and content;
changed source or a changed locator cannot become an adopted replacement.
Retirement refuses active reads and original pending FileHandles, retires its
actual reader sessions, then verifies the exact root identity, physical parent
and owner marker before recursive removal. A receipt-shaped object cannot grant
retirement. Failure retains original resource capabilities and fixture evidence;
the caller explicitly retires that original session after actual closure.

Seven authored, locally unrun cases cover closed preflight/no mutation, real
edit/delete/rename/re-add cohorts versus isolated rebuild, joined original-world rechecks and
source/pointer/marker tampering, and refusal to remove a world while its actual
source descriptor close is pending. Real builds have a25-second whole-run cap;
the existing runner remains at30 seconds, zero retries and native redo disabled.
The six build cases have one serial CI owner and no broad-lane overlap. Broader
semantic/build-world, certificate/test-suggestion adapters and an asynchronous
real-build minimizer remain required for #1528; this does not close that issue.
